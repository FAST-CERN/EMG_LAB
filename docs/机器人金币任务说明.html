机器人金币任务 · 教师与学生说明

版本：coin_race_v2 · 2026-10-25。此版用于课程练习和期末方案试运行，正式开赛前由教师公布并冻结最终规则。

任务与排名

用实时肌电控制统一的 G1 仿真机器人，依次接近场地内的金币。机器人骨盆在水平面上距当前金币中心不超过 0.45 米时收集成功，随后出现下一枚。每局从相同位置、朝向和姿态开始，固定站稳 3 秒后开始计时。

默认每局 6 枚、120 秒；每组完成 3 个规定种子各一局。两组使用相同种子、同一电脑、同一场景、同一运控策略和同一套按能力分档的控制规则。不同分类器、连续控制、混合控制进入同一榜单：

  1. 首先比较三局合计收集数（等价于总完成率，满分 18 枚）。
  2. 收集数相同时，比较三局合计计分用时，越短越好。
  3. 全部金币收集完成时，计分用时为实际完成时间；超时、跌倒、越界、主动退出或信号中断未完成时，该局计分用时为 120 秒，并保留已收集数。
  4. 两项均相同则并列。不分榜，时间不打折；进阶奖励只体现为通过教师验收后获得更高的速度上限。

计时采用单调墙上时钟，包含推理、滤波、控制反应和转向耗时，不能暂停或中途复位。仿真明显落后实际时间、数值错误或完整性校验失败的记录不自动计为有效正式成绩，由教师确认原因后决定重测，不能由学生自行挑选最佳一局。默认种子为 20261025、20261026、20261027，属于公开练习/试运行路线；正式种子由教师另行规定并冻结，提前公开多少由教师统一决定。

为什么统一限制速度

限制所有模型最终请求的运控指令，使比赛重点落在肌电表达、解码、响应与控制能力上。训练数据数量不设上限；速度表、机器人模型、步态策略、PD 参数、物理步长、加速度限制、收集半径和计时规则统一由教师程序管理。

如何获得进阶速度档

比赛奖励实际控制能力，不按模型名称或网络结构判断。以下两类能力通过一项即可；两项都实现也不叠加速度额度：

  • 连续幅度控制：操作者通过实时肌电自主、持续地调节某一运动分量，展示至少三个不同非零幅度以及停止，并能向大、向小调节。验收时看连续变化过程和指令记录；仅把固定类别换成几个速度、对固定类别插值/平滑、自动爬升速度，不足以证明该能力。
  • 混合控制：操作者能同时输出至少两个非零分量，并主动改变它们的相对比例，展示至少三种比例以及停止。仅快速交替单轴类别、始终保持固定对角线或固定转弯比例，不足以证明该能力。

教师用真实肌电看演示、检查解码代码与指令日志，记录组别、模型哈希、通过的能力和验收证据。不能用键盘、录制指令或自动读取金币位置完成验收。算法可以是分类、回归、规则或组合，只要最终控制能力符合上述要求；分类与肌电强度结合也可以申请进阶档。

未通过验收可继续使用基础档比赛。开发练习可以显式选择进阶档，但报告只能作为练习；正式局会核对教师验收表，不能靠更改 control_mode 或 speed_tier 自动获得资格。两档共用场景、路线、收集半径、时间规则、物理和运控策略，仍然同榜、完成率优先。

两类输入随后经过相同的平移 1.5 m/s²、旋转 2.5 rad/s²指令变化限制，以及相同的 Walk/Balance 运控策略。零转向的平移指令使用统一的直行方向补偿（最多 ±0.15 rad/s）。这些数值约束的是指令；惯性、平衡修正会使测量速度瞬时超出指令值。不能据此承诺任意信号下永不摔倒，更不能将仿真范围直接当作真机安全范围。

学生如何操作

  1. 选择机器人四类或七类任务，连接设备；采集、训练或导入对应模型。
  2. 在“04 使用模型”选择模型和数据来源，把“练习方式”设为“金币任务”。
  3. 填写组别、种子、金币数和限时，点击“开始推理”。站稳倒计时后开始。
  4. 金点表示当前目标，蓝点及短线表示机器人位置、朝向。小地图上方为场地 +X，左方为 +Y。目标不在主画面内时参考小地图和方位提示。
  5. 到达目标后自动出现下一枚。任务完成、失败或提前结束都会保存记录，可在主界面点击“打开最近一局报告”。

模拟设备、离线回放用于检查软件和练习，报告明确标为练习。回放使用原始肌电重新推理，标签不控制机器人；固定录制数据不能根据金币位置主动调整，不能代替现场闭环考核。正式比赛只接受真实 Cometa/Delsys 实时输入，且关闭 DDS 真机输出。

当前 GUI 已接通现有四类、七类 ONNX 模型。连续/混合控制的限幅、场景输入和计分接口已提供，尚未提供通用的连续模型导入/训练界面；学生实现解码器后，需提前与教师完成接口接入及验收，不应到比赛现场临时替换整套仿真程序。

教师赛前准备

比赛评定程序应放在教师控制的实验室电脑中。学生提交模型和解码代码，由教师审核接入；统一运控、场景、规则和计分模块不得由学生替换。模型自身不接收种子、金币坐标、仿真状态或目标标签，不允许键盘/鼠标代替肌电驾驶或自动寻路。操作者通过画面判断目标并作出肌肉动作。

设备只有一台时，训练数据量仍不限，但应向两组提供相同预约采集时长、相同比赛前佩戴校准时长和同样的练习机会。电极位置、通道、采样率、操作者和每次重新佩戴均应记录。建议每条线预先指定操作者，三局保持同一操作者和同一模型；比赛顺序按种子交替 A/B、B/A、A/B，避免一组总是先比。上述安排由教师提前统一公布。

教师在 competition_rules.json 中选择三个不同种子、统一金币数和限时。修改后先运行路线与稳定性测试；若改变范围、策略或机器人，必须重新实验验证。正式开始前固定两组模型与解码器，比赛期间不再训练或调参。

教师验收表 competition_approvals.json 初始为空。需在冻结前填入通过的条目，示意如下（哈希必须替换为提交模型文件的实际 SHA256）：

{"version":"coin_race_v2","entries":[{
  "approved":true,"group":"G01",
  "model_hashes":{"model.onnx":"64位小写哈希","metadata.json":"64位小写哈希"},
  "capabilities":["continuous_amplitude"],
  "approved_by":"验收教师","evidence":"验收日期与演示/日志保存位置"
}]}

capabilities 可为 continuous_amplitude、mixed_axes 或两者。Windows 可用 Get-FileHash 模型文件 -Algorithm SHA256 查值，并转换为小写填入。两组的解码接入代码与验收表须一起纳入同一个教师基准；不要给两组各自冻结不同的比赛程序。修改验收表、模型或解码代码后必须重新审核冻结，旧局与新基准不能混在一个榜单中。当前模型身份核对使用 model.onnx 与 metadata.json，其他自定义参数文件须在接入时纳入教师基准，不能赛中自由修改。

在项目目录运行：

.venv\Scripts\python.exe scripts\benchmark_competition_control.py --output verification\control_benchmark.json
.venv\Scripts\python.exe scripts\benchmark_coin_routes.py --output verification\coin_routes.json
.venv\Scripts\python.exe scripts\freeze_competition.py --confirm-reviewed

冻结脚本显式生成 competition_baseline.json，输出其 SHA256。请在教师独立保管的位置留存文件和哈希；程序不会在启动时自动重新生成基准。已有基准只有添加 --replace 才会替换，替换前须保留旧记录并重新验收。

正式模式会在开赛前和结束后校验代码、运控模型、场景、SDK、规则、脚本及主要依赖版本，并检查参赛模型文件是否改变。它可以发现与可信基准的差异，不能阻止拥有整台电脑写权限的人同时改程序和基准。因此本地学生自报分数不作为正式结果，需教师受控运行与复核。当前交付附带的是已测试版本的试运行基准，期末按最终规则重新审核冻结。

.venv\Scripts\python.exe scripts\rank_competition.py --baseline-sha256 教师独立保存的哈希 --output verification\leaderboard.csv A种子1\result.json A种子2\result.json A种子3\result.json B种子1\result.json B种子2\result.json B种子3\result.json

工具核对规定种子、路线、基准、模型固定性、指令记录和计分后输出统一 CSV。不同控制模式使用相同排序；输出 control_modes、speed_tier 信息列，三局须使用相同档位。计分用时不因控制方式获得折扣。正式赛保留所有尝试，教师另行记录重测原因，禁止删掉失败局再挑最好局。

已完成的运控实验

本轮共 645 个仿真用例：123 个单轴探索、204 个候选范围比较、194 个进阶档验证、84 个基础固定指令验证，以及两档各 20 条完整路线。探索阶段保留失败样本，用于排除不合适的速度；最终进阶档 194/194、基础固定档 84/84 均满足本轮稳定与停车指标。两档各 20 条路线均完成，理想测试控制器平均用时分别为 40.09 秒与 32.82 秒。

前进指令从 0.8 加到 1.0 m/s 时，测试中的停车漂移从约 0.47 增至 0.68 m，因此没有把更快但更难停车的范围直接开放。转向同样结合停止后的角度漂移选取，不能只以“没摔倒”决定上限。

实验报告见 运控范围实验与规则 v2，原始结果见 verification/control_envelope_v2/。路线测试使用仅用于验证的几何导航器，证明可达性和速度额度有实际效果，不能作为学生控制器。它不代表肌电比赛成绩；最终手感仍需用实时肌电和人工操作复核。旧 control_benchmark.json、coin_routes.json 是 v1 的历史记录，不是本次 v2 验证结果。

开发接口与模块边界

  • emg_lab/competition.py：规则、独立于参与者轨迹的路线生成、计时、收集、失败原因、记录与完整性校验。
  • emg_lab/physics/worker.py：比赛生命周期、固定分类映射、连续输入接收、失联停止、物理步与渲染。
  • emg_lab/physics/commands.py：七类动作表和连续请求的共同范围。
  • emg_lab/physics/simulation.py：原有 MuJoCo 物理、Walk/Balance 策略和 PD；新增 set_velocity([vx,vy,wz]) 接口，不直接写机器人位置来制造移动。
  • emg_lab/physics/scene.py、robot.py：金币窗口、小地图和 command(class_id) / velocity(vector) 输入。
  • emg_lab/app.py：选择比赛设置，原 Session → InferencePipeline → filtered_class 驱动场景。

扩展连续解码器时，构造 RaceConfig(control_mode='continuous', speed_tier='basic')；进阶档使用 speed_tier='advanced'，在每次新推理结果后调用 RobotScene.velocity([vx,vy,wz])。分类局调用 command(int_class)。两种接口不可在同一局临时切换；输入必须有限数值。场景准备完毕、模型/设备开始后调用 arm_competition()。超过 0.75 秒没有新指令则停止，持续缺失会结束本局。接入代码仍需教师审核，不能仅通过调用这些公开 Python 方法获得可信执行隔离。
